Architectural principle

Automation is a system, not a collection of scripts.

Tests express behavior. Shared framework layers own reusable data, authentication, API interaction, browser abstractions, validation, lifecycle and execution responsibilities.

01

Behavior

Test scenarios communicate what product behavior or quality characteristic is being evaluated.

02

Reusable infrastructure

Fixtures, factories, clients and page abstractions own shared technical concerns.

03

Execution ownership

Each quality concern runs only where its responsibility requires execution.

API architecture

Validate external boundaries at runtime.

TypeScript protects framework code at compile time. TypeBox and AJV verify that external API responses actually satisfy the expected contract at runtime.

Domain client → HTTP response → Status validation → AJV contract → Business assertion

Runtime validation creates an explicit trust boundary between the framework and the external provider.

Browser architecture

Reusable behavior without hiding scenario intent.

Browser-facing responsibilities are separated into reusable page and component abstractions while tests retain ownership of scenario-specific expectations.

Page Objects

Major application surfaces

Encapsulate meaningful browser interactions instead of scattering selectors through test code.

Component Objects

Reusable interface behavior

Represent independent UI components when they own meaningful behavior of their own.

Fixtures

Capability composition

Provide prepared pages, authentication, APIs and lifecycle responsibilities to scenarios.

Assertions

Scenario ownership

Keep the reason for a failure visible at the test level where appropriate.

Quality ownership

Execution follows responsibility.

Different quality characteristics have different execution requirements. The architecture makes those differences explicit.

UI

Browser performance

Reproducible execution

Docker is part of the architecture.

Containerized execution aligns runtime dependencies, browsers, visual rendering and CI behavior around a controlled execution boundary.

Source → Docker image → Known runtime → Quality responsibility → Evidence

The container owns the execution environment. The test project and CI job own the quality responsibility.

Engineering principles

Coherence before abstraction growth.

New capabilities should reuse and extend existing ownership boundaries before introducing parallel implementations.

01

Discover

Understand existing capabilities before designing new ones.

02

Reuse

Prefer an existing responsibility when it already fits.

03

Extend

Grow existing infrastructure when ownership remains coherent.

04

Create

Introduce a new abstraction only when a real boundary exists.

05

Validate

External boundaries require runtime evidence, not assumptions.

06

Diagnose

Evidence exists to support engineering decisions and RCA.

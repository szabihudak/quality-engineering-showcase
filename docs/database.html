Quality layer · Database

Database validation.

Persistence is checked across the application and database boundary, without moving application setup or business behavior into the database layer. The database layer verifies what was stored; API and UI tests still verify the behavior.

Validation model

API or fixture setup ↓ Application behavior ↓ Domain database client ↓ Persisted PostgreSQL state ↓ Spec assertions

Responsibilities

Spec → Fixture → Domain database client → DatabaseClient → PostgreSQL
  • DatabaseClient owns the PostgreSQL connection and its lifecycle.
  • Domain database clients own the domain queries and map the stored records; their SQL is parameterized, which the architecture lint enforces.
  • Specs own the assertions; there is no raw SQL in a spec.
  • API clients, fixtures and factories create the application state, as in every other test.

Where it runs

Database tests run in their own browser-independent Playwright project, once, not multiplied across browsers. They run only in an environment whose configuration allows database access, and they are not retried, so the state a failure leaves stays clear and no duplicate data is created.

tests/database/** → --project=database → only where allow.database is true

Test data lifecycle

Each test creates unique data and keeps what it leaves behind, so a failure can be investigated in the database. Deleting data after every test is not the default.

Create unique application state ↓ Validate persistence ↓ Keep the state for diagnosis

Guarded reset

A destructive reset is a separate, explicit operation, allowed only where the environment permits it. It fails closed when a safety condition is not met, and the application stays the source of truth for the schema and the seed data.

Reset request ↓ Check the test environment and its permission ↓ Check the database configuration ↓ Require explicit confirmation ↓ Restore the application schema and baseline seed data ↓ Verify the baseline

Evidence

This page documents the database architecture and lifecycle. Unlike the other quality layers, there is no public report of a database run: a sanitized one has not been published, and the page does not present architecture as execution evidence.

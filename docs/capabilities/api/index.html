Engineering responsibility

Validate behavior before trusting types.

Compile-time TypeScript types describe what the framework expects. They do not prove that an external provider actually returned that structure at runtime.

01

Transport validation

The framework verifies expected HTTP behavior before moving to payload-level assertions.

02

Runtime contract validation

TypeBox schemas and AJV validate the real provider response before business assertions trust the parsed data.

03

Business behavior

Scenario-level assertions then validate observable application behavior on top of the verified contract.

Contract pipeline

Schema-first runtime verification.

The contract layer sits between raw provider data and business assertions so malformed successful responses do not silently pass through typed test code.

Authentication boundaries

Successful and rejected behavior are both testable contracts.

A controlled rejection is a successful test result when the API returns the expected security behavior and error contract.

Deterministic setup

Generated data instead of shared accounts.

Test factories create unique execution data so scenarios remain independent from manually maintained users and previously created application state.

Scenario → Factory → Unique data → API execution → Assertions

Synthetic @example.com identities visible in the execution report are generated automation data and do not represent real users.

Provider behavior

Defaults are observable contract behavior.

Optional request fields are validated against the behavior exposed by the provider rather than duplicated as implementation logic inside the test framework.

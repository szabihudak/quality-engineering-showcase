Engineering responsibility

Verify persistence without replacing application behavior.

Database validation confirms that supported API and application actions produce the expected persisted state. Direct SQL remains a verification boundary rather than an alternative path for creating business state.

Architecture

Database responsibilities remain explicit.

Transport, domain queries and test assertions are separated so database access does not become a collection of SQL statements embedded directly inside test specifications.

Execution ownership

Database validation executes once.

Persistence behavior is browser-independent, so database tests have their own Playwright project instead of being multiplied across Chromium, Firefox and WebKit.

tests/database/** → project=database → PostgreSQL → Persistence assertions

Automatic retries are disabled for this project. Database tests create persistent state, so retrying a failure could introduce additional records and obscure the original failing condition.

Test data lifecycle

Preserve failures, reset explicitly.

Normal execution uses unique generated data and intentionally preserves resulting database state. A destructive reset is a separate guarded operation rather than an implicit test teardown.

Safety boundary

Destructive operations fail closed.

Direct database access and reset behavior are restricted to the dedicated containerized test environment and require explicit runtime configuration.

TEST_ENV=localDocker → DATABASE_URL → CONFIRM_DB_RESET=true → Reset permitted

The connection string is supplied at runtime and is not owned by repository environment configuration. The framework does not log the full database connection string.

Schema ownership

The framework validates persistence, not application schema ownership.

Database schema creation and baseline seed logic remain owned by the target application. The test framework orchestrates reset and verifies the resulting baseline instead of duplicating those definitions.

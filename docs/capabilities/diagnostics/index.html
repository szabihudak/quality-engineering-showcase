Engineering responsibility

A red result needs classification, not assumption.

Failed automation does not automatically mean broken automation. Diagnosis begins by identifying which system responsibility actually produced the failure.

01

Collect evidence

Reports, screenshots, runtime output and failure artifacts preserve enough context for investigation.

02

Reproduce behavior

Reproducibility helps distinguish stable product behavior from transient environment or infrastructure failures.

03

Classify root cause

Failures are assigned to the product, framework, environment, infrastructure or external platform as evidence supports.

Diagnostic model

Failure domains

Separate ownership before remediation.

Different failure domains require different responses. Root-cause classification prevents framework changes from being used to hide genuine application defects.

Product

Application behavior

Real quality defects exposed by correctly functioning tests.

Framework

Automation implementation

Incorrect locators, fixtures, assertions or framework logic.

Environment

Target state

Configuration or deployment conditions affecting execution.

Infrastructure

Execution platform

Runtime, network, container or CI infrastructure problems.

Root-cause conclusion

The framework behaved as designed.

Repeated detection across two application states supports a product-defect classification rather than an isolated automation failure.

axe-core violation → zero-violation assertion fails → issue reproduced → framework confirmed → product defect

The correct engineering response is to preserve and investigate the product signal, not weaken the quality gate.
